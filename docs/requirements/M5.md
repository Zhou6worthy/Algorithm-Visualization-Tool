# M5 实施任务：第二算法纵向闭环验证（AI Algorithm Visualizer）

## 一、项目背景与当前定位

本项目是一个 **AI 算法课堂备课与演示辅助工具**。

核心使用场景是：教师输入算法题目、源码、解题思路和多个测试用例，系统执行算法并生成可视化过程，教师可以在课堂上手动控制演示，也可以一键自动播放。

M4 已完成 Two Sum 的前后端整合：

- Vue 3 + TypeScript + Vite 前端工作台。
- FastAPI 后端及 SQLite 项目持久化。
- GUI 创建、编辑、保存项目和测试用例。
- 后端执行真实代码，生成 ExecutionTrace 和 AnimationTrace。
- Vue 播放器消费后端返回的数据。
- 支持多测试用例、播放控制、代码高亮、变量和数据结构展示、课堂提示。
- M4 报告声称 pytest 111 passed，真实 Edge E2E 33 项通过。

当前系统已经形成 Two Sum 的端到端闭环，但尚未证明它具备真正的多算法扩展能力。

本阶段目标不是重写系统，而是通过接入第二种算法，验证现有架构能否支持不同算法的执行追踪、语义转换、视觉组件装配和课堂演示。

## 二、M5 核心目标

完成一个第二算法的完整纵向闭环：

**GUI 输入题目、源码和测试用例 → 后端执行真实代码 → 生成 ExecutionTrace → SemanticAdapter 转换 → AnimationTrace → AlgorithmProfile / VisualPlan 装配 → Vue 动态组件渲染 → 教师控制播放 → 课堂提示。**

必须通过真实 GUI 和真实浏览器验证整个流程。

本阶段只选择一种第二算法，不追求一次性支持所有算法。

## 四、第二步：选择第二种算法

根据现有架构和组件能力，选择一种与 Two Sum 有明显差异的算法。

候选方向：

- 二分查找：适合验证区间变化、左右边界和搜索状态。
- 链表反转：适合验证指针关系和节点连接变化。
- DFS/BFS：适合验证图结构、访问状态和遍历过程。
- 排序算法：适合验证数组交换、比较和多轮执行过程。

请结合现有组件、追踪能力和改造成本，选择最适合的一种。

要求：

1. 只能选择一种算法。
2. 不能只因为它最容易复用 Two Sum 的 ArrayView 就选择它。
3. 应尽量体现与 Two Sum 不同的执行语义和视觉需求。
4. 如果现有架构无法支持候选算法，应说明原因，并选择更合适的替代方案。
5. 选择后说明为什么它适合验证当前架构的扩展能力。

## 五、第三步：实现第二算法的后端追踪链路

必须实现第二算法的真实执行追踪，而不是根据预设答案模拟动画。

至少完成：

### 1. 真实执行

- 使用现有执行器执行用户提供的算法源码。
- 保留真实输入、输出和执行过程。
- 支持多个测试用例。
- 每个 CaseRun 必须拥有独立的执行轨迹。
- 切换用例时不能混用不同用例的轨迹。
- 正确处理正常执行、结果不匹配、执行异常等情况。
- 不允许为执行失败的用例伪造 AnimationTrace。

### 2. SemanticAdapter

为第二算法实现独立的语义适配器。

要求：

- 将底层 ExecutionTrace 转换为统一 AnimationTrace。
- 不修改 M1/M2 已有 Two Sum 追踪逻辑。
- 不在通用执行器中写大量算法专属判断。
- 算法专属语义应放在对应 Adapter 中。
- 对不支持的执行事件，应明确处理或记录，不得静默生成错误动画。

### 3. AlgorithmProfile

实现或扩展算法 Profile 注册机制。

Profile 至少负责：

- 算法标识。
- 对应 SemanticAdapter。
- 视觉组件需求。
- 变量和状态投影。
- 教学提示素材。
- VisualPlan 配置。
- 必要的复杂度信息。

要求：

- Two Sum 和第二算法都通过统一机制注册。
- 新增算法不应要求在多个核心模块中重复添加 `if algorithm == ...`。
- 不要为了未来可能出现的算法设计庞大而空泛的插件系统。
- 优先实现当前两个算法确实需要的最小可用注册机制。

## 六、第四步：验证 VisualPlan 与 Vue 组件动态装配

这是本阶段最重要的架构验证点之一。

M4 报告已经明确指出：

> Vue 组件目前主要按照 Two Sum 的四类视觉组件布局，VisualPlan 还没有完全驱动动态组件注册和装配。

M5 必须针对这一问题进行验证和改进。

要求：

1. Vue 前端应能够根据后端返回的 VisualPlan 或等价的组件描述，决定展示哪些视觉组件。
2. 建立明确的前端组件注册机制。
3. 组件注册机制负责将组件类型映射到 Vue 组件。
4. 不应在主工作台中堆积大量针对具体算法的条件分支。
5. 不应让 ArrayView、HashMapView 等通用组件直接读取 Two Sum 的业务变量。
6. 通用组件只消费统一的视觉状态、动画步骤和组件上下文。
7. 算法专属的数据投影由 Profile 或 Adapter 完成。
8. 第二算法需要的新视觉组件可以新增，但不能为了接入它而破坏已有 Two Sum 组件。

需要特别区分：

- AlgorithmProfile：算法语义和视觉需求。
- VisualPlan：组件类型、布局、槽位及视觉配置。
- Vue Component Registry：组件类型到实际 Vue 组件的映射。
- Vue Component：只负责展示传入的数据。

不要把上述职责混在一个文件或一个大型组件中。

如果现有架构已经具备其中某些能力，应优先复用，不要重复建设。

## 八、第六步：课堂教学内容

第二算法必须拥有对应的教学提示。

教学提示应服务教师讲解，而不是机械播报程序事件。

至少覆盖：

- 算法当前处于什么阶段。
- 当前关键操作是什么。
- 为什么执行这个操作。
- 当前状态发生了什么变化。
- 下一步可能发生什么。
- 这一阶段适合向学生提出什么问题。
- 对应问题的参考答案。
- 常见错误或容易混淆的知识点。

示例：

不要只写：

“当前 left 从 0 变为 1。”

应尽可能写成：

“当前搜索区间已经缩小。由于中间位置的值小于目标值，因此左边界需要向右移动。可以让学生先判断：如果目标值比中间值大，为什么左半部分可以不再考虑？”

具体讲解内容应根据所选算法设计，不要照搬上述示例。

本阶段不要求接入实时 LLM，不要求 TTS。

### 代码执行安全

当前项目的 LocalSandbox 不应被描述为生产级安全沙箱。

本阶段不要把“可以执行用户输入的源码”宣传为“可以安全执行任意外部代码”。

- 本机个人使用、执行自己信任的代码，与执行学生提交、陌生人代码或网络上传代码，是不同的风险等级。
- 仅监听 `127.0.0.1` 不等于代码执行隔离。
- 不要在没有真实隔离、资源限制和安全测试的情况下宣称 DockerSandbox 已具备生产级防护。
- 如果本阶段只用于本机可信代码，可记录为已知限制。
- 如果准备开放给其他用户提交代码，则必须优先设计安全执行隔离，不得直接开放现有执行接口。
